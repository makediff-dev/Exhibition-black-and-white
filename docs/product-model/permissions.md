# Права доступа

Принцип: **deny by default**. Доступ только участнику объекта и сотруднику с явным правом. Три проверки: маршрут, чтение, mutation.

Доказательства: playbook §6.2; аудит №1, 2, 15, 17, 18; `cabinet-scope.ts`; `account/[role]/[[...slug]]/page.tsx`.

Ограничение прототипа: backend нет. Этап 2 может дать только **демо-адаптер** на клиенте. Это не production security boundary.

Открытые решения: D-01, D-02, D-07, D-09. Временные правила ниже помечены `TEMPORARY`.

## Акторы

| Актор | Код | Как устроен сейчас | Целевой контракт |
|---|---|---|---|
| Заказчик | `customer` | `DEMO_USERS.customer`, `user.id` = `user-customer` | Организация-заказчик; видит только свои заявки/сделки/документы |
| Исполнитель | `contractor` | Профиль + `getContractorIdForUser` → `ctr-*` | Видит подходящие published-заявки и свои отклики/сделки |
| Площадка | `venue` | `getVenueIdForUser` → `venue-1` | Только объекты своей площадки, где она сторона |
| Организатор | `organizer` | `user.id` = `user-organizer` | Только свои мероприятия и объекты, где он сторона |
| Сотрудник | `employee` | Списки в store, UI-галочки | Нет логина. **TEMPORARY:** права сотрудников не enforce |
| Гость | `guest` | нет сессии | Публичный каталог; мутации кабинета запрещены |
| Демо-оператор | `demo` | `DemoMenu` | Не роль продукта. Отдельный инструмент |

**TEMPORARY (D-01, D-02):** в одной сессии ровно одна рабочая роль и одна организация. Переключение — только через явный switch аккаунта (`switchAccount`) или повторный демо-вход. Параллельные роли в одном UI запрещены. CTA другой роли не показываются как primary (аудит №18).

## Три уровня проверки

| Уровень | Сейчас | Цель |
|---|---|---|
| 1. Маршрут | Client `useEffect`: чужой `/account/{role}` всё равно рисует `AccountPageRenderer`, потом `replace` | Не рендерить чужой кабинет. 403 или безопасный переход **до** контента |
| 2. Чтение | `isDocumentForUser`, `isPaymentForUser`, `isDealForUser`, `isRequestVisibleToContractor` | Те же правила в одном адаптере; фильтр по сторонам, не по «есть venueId» |
| 3. Mutation | Кнопки в UI; часть действий без проверки роли | Та же матрица на accept/reject/publish/sign/pay |

`isAllowedCabinetPath` — allowlist slug, не ACL объекта.

## Известные дыры (не закрывать молча в UI)

1. **Кабинет (№1).** `user.role !== url.role` не блокирует первый render.
2. **Документы (№2).** Для `venue`: `document.venueId === venueId`. Seed вешает `venue-1` на договоры «Заказчик — Исполнитель». Для `organizer`: любой `organizerId === user.id`.
3. **Заявки (№7).** `isRequestVisibleToContractor` проверяет только `published` и closed-invite. Нет категории/гео. Нет дедлайна.
4. **Платежи.** Venue/organizer режутся по `venueId`/`organizerId`. Зеркальный `opay-7` (резерв deal-1) виден организатору, хотя сделка customer–contractor.
5. **Выход (№15).** `logout()` чистит persist, но нет серверной сессии: Back + восстановление — риск гидратации, если guard слабый.
6. **Контакт площадки (№17).** Авторизованный заказчик уходит на `/register`.
7. **Сотрудники.** Галочки permissions не применяются к маршрутам.

## Правило документа (TEMPORARY D-07)

Документ виден организации, если она **сторона**:

- структурированные поля `partyIds: { role, organizationId }[]` (цель);
- пока в коде строка `parties` + опциональные `venueId`/`organizerId`/`dealId`.

**Нельзя** выдавать документ по одному только `venueId` или `organizerId`.

Подпись: только сторона с правом `sign` и статусом документа `sent`. Сотрудник без `documents` + sign — нет. Пока employee login нет — подписывает демо-админ организации.

## Правило заявки для исполнителя (TEMPORARY D-09)

Исполнитель видит `published` заявку, если:

- `closed_request` → он в `invitedContractorIds`; **или**
- иначе пересечение `request.category` с `profile.categories` **и** пересечение города заявки с `profile.cities` / geography.

Если пересечения нет — объекта нет в списке (не «вижу, но не могу»). Расширение специализации — отдельный явный сценарий, не текущий список.

После `deadline` / `responseDeadlineAt` — нет `submit_proposal`.

## Запрещённые состояния UI

| Ситуация | Поведение |
|---|---|
| Нет права на маршрут | 403 с объяснением роли **или** переход в свой кабинет. Не смесь меню A + контент B |
| Нет права на объект | Пусто / 403 объекта, не «чужой список» |
| Действие недоступно | Кнопка отсутствует или disabled + `blockedReason` + recovery |
| Гость открывает кабинет | `/login?returnUrl=` |
| CTA другой роли | Не primary. Если нужен переход роли — явное подтверждение (после D-01) |

## Приёмка этапа 2 (контракт, не реализация)

- Прямой URL каждого из 4 кабинетов под каждой из 4 сессий.
- Документ customer–contractor не виден площадке и наоборот.
- Закрытая заявка не видна неприглашённому.
- `/deals/{id}` чужой сделки — 403.
- Logout → `/login`; повторный вход по Back без сессии не показывает кабинет (в рамках клиента — persist пуст + guard до render).
